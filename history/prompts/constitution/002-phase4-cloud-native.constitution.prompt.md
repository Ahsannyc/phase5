## 1. Core Philosophy & Binding Rules

1. Strict Spec-Driven Development (SDD)
   - Specifications are the single source of truth.
   - All code (Dockerfiles, Helm charts, manifests, configs) must be generated by Claude Code from approved Markdown specs.
   - Manual coding is forbidden except for very minor formatting fixes.
   - Every deployment artifact starts with spec → plan → tasks → implement → test.

2. No manual coding outside Claude Code
   - Use `sp specify`, `sp plan`, `sp implement` workflow.
   - All agents must reference constitution.md and relevant @specs/... files.

3. Agent & Skill Boundaries (Strict)
   - Spec Writer → specs only (never code)
   - Architecture Planner → plans & architecture.md only
   - Database Engineer → SQLModel models & migrations only
   - Backend Engineer → FastAPI endpoints & logic only
   - Frontend Engineer → Next.js UI & ChatKit only
   - ChatKit Frontend Agent → ChatKit config & chat UI only
   - MCP Engineer → MCP server & tools only
   - AI Agent Engineer → OpenAI Agents SDK runner & prompt only
   - Integration Tester → end-to-end tests only
   - Deployment Engineer (new) → Dockerfiles, Helm charts, K8s manifests only

4. Always require spec approval
   - Every coding agent must ask:
     "Are the relevant specs (e.g. Docker / Helm / K8s / Deployment) approved?"
     before generating any code or manifest.

5. Multi-user & Security is mandatory
   - Every task & conversation belongs to exactly one user (enforced by user_id)
   - JWT verification on every protected endpoint (401/403)
   - No cross-user data access allowed — ever

## 3. Phase 4 Specific Requirements (must be satisfied)

- Dockerize frontend (Next.js standalone) & backend (FastAPI)
- docker-compose.yml for local multi-service testing
- Helm chart for Kubernetes deployment (with values.yaml overrides)
- Deploy & verify full app (frontend + backend + chatbot) on Minikube
- Use kubectl-ai or kagent for at least one meaningful operation
- Prepare for cloud scaling (stateless pods, Neon external DB)
- Document every deployment step in README & deployment.md

## 4. Quality, Security & Style Rules – Phase 4

- Multi-stage Dockerfiles → minimal images
- Non-root users in containers
- No secrets in images or Git
- Helm chart must be parameterized (values.yaml)
- Include liveness/readiness probes
- Health checks & startup probes
- Use Minikube addons: ingress, metrics-server
- Document all commands & troubleshooting

## 5. Workflow & Phase 4 Progression

1. Spec Writer creates/refines deployment specs
2. Architecture Planner updates architecture.md & Helm structure
3. Engineers create Dockerfiles
4. Create Helm chart (via Helm CLI or Claude)
5. Deploy to Minikube
6. Use kubectl-ai / kagent for AIOps tasks
7. Integration Tester verifies full K8s deployment
8. Document everything

## 6. Phase 4 Success Criteria

- App runs locally via docker-compose
- App deploys successfully to Minikube via Helm
- Helm chart supports install/upgrade/uninstall
- Chatbot, auth, tasks all work inside Kubernetes
- kubectl-ai or kagent used for at least one operation
- README has clear setup & deployment instructions
