# Todo Phase 2 Constitution

## Core Principles

### Specification-Driven Development (NON-NEGOTIABLE)
All implementation must be derived from approved Markdown specs located in `/specs/`. No agent may write code without an approved relevant spec. This ensures traceability and quality control throughout the development process.

### Strict Agent Boundaries
Agents have strict boundaries: Spec Writer → only creates/refines specs (never code); Architecture Planner → only creates planning documents; Database Engineer → only writes SQLModel models in `/backend`; Backend Engineer → only writes FastAPI code in `/backend`; Frontend Engineer → only writes Next.js code in `/frontend`; Integration Tester → only runs/tests after others report completion. This ensures focused responsibility and reduces cross-contamination.

### Multi-User Security Enforcement
Every task belongs to exactly one user (enforced via `user_id`). No endpoint or UI may show tasks from other users. All API endpoints that read/write tasks **must** verify JWT and match `user_id`. This ensures data isolation between users.

### Spec Approval Requirement
Every coding agent (Database, Backend, Frontend) **must** ask: "Are the relevant specs (e.g. API + Database / UI + API) approved?" before generating any code. This ensures all implementations are properly specified first.

### No Manual Coding Outside Claude Code
All code must be generated by Claude Code based on specs. Manual edits are only allowed to fix formatting or very minor typos — never logic. This maintains consistency and traceability of all changes.

## Technology & Stack Decisions

### Monorepo Structure
The project follows this structure: `frontend/` (Next.js 16+ App Router, TypeScript, Tailwind), `backend/` (FastAPI + SQLModel + Alembic), `specs/` (all specifications), `skills/` (reusable code snippets), `subagents/`, `tests/`, `docker-compose.yml`, `.env.example`, and `constitution.md`. This ensures organized separation of concerns.

### Frontend Stack
Frontend uses Next.js 16+ (App Router), TypeScript, Tailwind CSS, Better Auth (with JWT plugin enabled), Server Components by default, Client Components only when necessary, and a centralized API client (`lib/api.ts`) with automatic JWT header attachment. This provides a modern, secure frontend architecture.

### Backend Stack
Backend uses FastAPI (async), SQLModel (ORM + Pydantic models), Neon PostgreSQL (serverless), JWT verification using `BETTER_AUTH_SECRET`, Alembic for migrations, and dependency injection for current user (`Depends(get_current_user)`). This ensures a robust and scalable backend.

### Authentication & Security
Better Auth handles signup/signin/session on frontend, backend verifies JWT on protected endpoints, JWT payload must contain `sub` = user_id (integer), token validation failure → 401 Unauthorized, wrong user_id in path → 403 Forbidden. This enforces secure authentication and authorization.

### Database Design
Database tables include `users` and `tasks`, with `tasks.user_id` as foreign key to `users.id`. All task queries **must** filter by authenticated `user_id`. This ensures user data isolation at the database level.

### Error Handling
Return correct HTTP status codes: 400 – validation error, 401 – missing/invalid token, 403 – authenticated but not authorized (wrong user), 404 – resource not found, 500 – unexpected server error (minimal info to client). This provides consistent error responses.

## Quality & Style Guidelines

All code must be clean, readable, and well-commented. Use English docstrings & comments. Follow PEP 8 (backend) and prettier defaults (frontend). Prefer async/await over blocking calls. Use type hints everywhere possible. Write self-documenting code (good names > comments). Avoid magic strings/numbers — use constants or enums when appropriate. This ensures maintainable, professional-quality code.

## Workflow Rules

1. Spec Writer creates/refines spec → gets approval
2. Architecture Planner updates architecture.md if needed
3. Database Engineer implements models/migrations (if schema changed)
4. Backend Engineer implements API routes & logic
5. Frontend Engineer implements UI & API integration
6. Integration Tester runs full flow verification
7. Fix bugs → update spec first → re-implement

This sequential workflow ensures proper coordination between team members and prevents conflicts.

## Governance

Specifications are the single source of truth. No manual coding outside of Claude Code. Agents have strict boundaries. Always ask for spec approval. Multi-user & Security is non-negotiable. This constitution is binding for all agents during Phase 2. Any proposed deviation must be explicitly discussed and approved. All implementations must comply with these governance rules.
