# Todo Phase 5 Constitution: Advanced Cloud Deployment & Event-Driven Architecture

Evolution of Todo Hackathon – Spec-Driven Development

Builds on Phases 1-4. Phase 5 mandates full implementation of advanced features, event-driven architecture (Kafka + Dapr), and production-grade cloud deployment (AKS/GKE/OKE) with GitOps and comprehensive observability.

**This constitution is BINDING for Phase 5. All agents must reference it. Any deviation requires explicit approval.**

## Core Principles (Phases 1-5)

### Specification-Driven Development (NON-NEGOTIABLE)
Specifications are the **single source of truth** — executable and generative. All code, manifests, Helm charts, CI/CD workflows, Dapr components, and Kafka configurations **MUST** be generated by Claude Code from approved specs in `/specs/`. No agent may write code without an approved relevant spec. Every feature starts with: **spec → plan → tasks → implement → test**. No manual coding allowed except very minor formatting fixes. This ensures traceability and quality control throughout the development process and guarantees code consistency with specifications.

### Strict Agent Boundaries (Phase 4-5: Fully Expanded)
Agents have strict boundaries:
- **Spec Writer** → only creates/refines specs (never code)
- **Architecture Planner** → only creates planning documents & architecture.md
- **Database Engineer** → only writes SQLModel models & migrations
- **Backend Engineer** → only writes FastAPI endpoints & logic
- **Frontend Engineer** → only writes Next.js UI code
- **ChatKit Frontend Agent** → only configures ChatKit & chat UI
- **MCP Engineer** → only implements MCP server & tools
- **AI Agent Engineer** → only implements OpenAI Agents SDK runner & prompt logic
- **Advanced Features Engineer** → only implements intermediate/advanced features (recurring tasks, due dates, priorities, tags, search/filter/sort)
- **Event-Driven Architect** → only designs event-driven architecture & Kafka/Dapr patterns
- **Dapr Specialist** → only configures Dapr sidecars, components, state store, bindings
- **Dapr Kafka Engineer** → only implements Kafka producers/consumers via Dapr
- **Cloud Deployment Engineer** → only provisions real cloud clusters (AKS/GKE/OKE) & deploys via Helm
- **Blueprint GitOps Engineer** → only creates reusable Helm blueprints & GitOps (ArgoCD/Flux) patterns
- **K8s Production Hardening** → only applies security & resilience controls (NetworkPolicy, RBAC, HPA, PDB, etc.)
- **Observability AIOps Agent** → only configures monitoring (Prometheus/Grafana/Loki), alerting, AIOps tools (kubectl-ai, kagent)
- **Cloud Deployment Engineer** → only handles cloud cluster provisioning & deployment orchestration
- **Integration Tester** → only runs/tests after others report completion

This ensures focused responsibility and reduces cross-contamination.

### Multi-User Security Enforcement
Every task and conversation belongs to exactly one user (enforced via `user_id`). No endpoint or UI may show tasks from other users. All API endpoints that read/write tasks or conversations **must** verify JWT and match `user_id`. This ensures data isolation between users.

### Spec Approval Requirement
Every coding agent (Database, Backend, Frontend, MCP, AI Agent, Deployment) **must** ask: "Are the relevant specs (e.g. API + Database / UI + Chat / MCP + Agent / Docker + Helm + K8s) approved?" before generating any code or manifest. This ensures all implementations are properly specified first.

### No Manual Coding Outside Claude Code
All code and deployment artifacts must be generated by Claude Code based on specs. Manual edits are only allowed to fix formatting or very minor typos — never logic. This maintains consistency and traceability of all changes.

### Frontend Stack (Phase 1-3)
Next.js 16+ (App Router), TypeScript (strict), Tailwind CSS (utility classes only), Better Auth (with JWT plugin enabled), OpenAI ChatKit (conversational UI), Server Components by default, Client Components only when necessary, centralized API client (`lib/api.ts`) with automatic JWT header attachment. Environment: `NEXT_PUBLIC_OPENAI_DOMAIN_KEY` (domain allowlist). This provides a modern, secure frontend with conversational UI.

### Backend Stack (Phase 1-3)
FastAPI (async), SQLModel (ORM + Pydantic models), Neon PostgreSQL (serverless, external), JWT verification using `BETTER_AUTH_SECRET`, Alembic for migrations, OpenAI Agents SDK (agent + runner + tool calling), Cohere API (primary LLM for chat completions), dependency injection for current user (`Depends(get_current_user)`), async SQLAlchemy sessions. This ensures a robust and scalable backend with AI capabilities.

### Deployment & Cloud-Native Stack (Phase 4 Base)
- **Docker 24+** (containerization)
- **Docker Compose v2** (local multi-service orchestration)
- **Minikube** (local Kubernetes cluster for development & testing)
- **kubectl** (Kubernetes CLI)
- **Helm 3+** (package manager for Kubernetes)
- **AIOps**: kubectl-ai + kagent (AI-assisted Kubernetes operations)
- **Neon PostgreSQL** (external, cloud-hosted database)

### Phase 5 Additions: Event-Driven & Real Cloud Deployment

**Kubernetes & Cloud Infrastructure**:
- Real cloud clusters (Azure AKS, Google GKE, Oracle OKE) — NOT Minikube
- Kubernetes 1.27+ with production-grade node pools

**Event-Driven Architecture**:
- **Kafka**: Self-hosted (Strimzi operator) OR managed (Redpanda Cloud preferred, Confluent Cloud, CloudKarafka, Aiven)
- **Kafka Topics**: `task-events` (create/update/delete), `task-updates` (state changes), `reminders` (scheduled reminders)
- **Dapr 1.14+**: Full building block integration (Pub/Sub, State, Bindings, Secrets, Service Invocation)

**CI/CD & Deployment**:
- **GitHub Actions**: Automated build → test → push images → deploy workflow
- **Container Registry**: ACR (Azure), GCR (Google), OCIR (Oracle) for storing images
- **Helm 3+**: Parameterized charts for multi-environment deployment (dev/staging/prod)
- **GitOps**: ArgoCD or Flux (Git is source of truth for all infrastructure)

**Observability & Operations**:
- **Monitoring**: Prometheus (metrics collection) + Grafana (dashboards)
- **Logging**: Loki (log aggregation) or cloud-native equivalents
- **AIOps**: kubectl-ai + kagent for intelligent cluster operations
- **Alerting**: AlertManager for critical metrics (error rate, latency, pod restarts)

**Security & Secrets**:
- External-secrets operator or cloud KMS (Azure Key Vault, GCP Secret Manager, OCI Vault)
- NetworkPolicy: deny-all ingress by default; specific rules for allowed traffic
- RBAC: least-privilege service accounts and roles
- Pod Security Admission: prevent privileged escalation
- Non-root containers: all workloads run as non-root users

This enables event-driven, scalable, production-grade cloud deployment with real Kubernetes infrastructure, full observability, and production-grade security.

### Authentication & Security
Better Auth handles signup/signin/session on frontend, backend verifies JWT on protected endpoints, JWT payload contains `sub` = user_id (integer), token validation failure → 401 Unauthorized, wrong user_id in path → 403 Forbidden. All protected API endpoints must validate JWT and match user_id. This enforces secure authentication and authorization.

### Database Design
Database tables include `users`, `tasks`, `conversations`, and `messages`, with `tasks.user_id` and `conversations.user_id` as foreign keys to `users.id`. All task and conversation queries **must** filter by authenticated `user_id`. This ensures user data isolation at the database level.

### Error Handling
Return correct HTTP status codes: 400 – validation error, 401 – missing/invalid token, 403 – authenticated but not authorized (wrong user), 404 – resource not found, 500 – unexpected server error (minimal info to client). For chat endpoints, return friendly error messages in the response. This provides consistent error responses.

## Phase 5 Scope & Mandatory Deliverables

### Part A – Advanced & Intermediate Features (MUST be implemented)
- **Recurring Tasks**: with schedule rules (daily, weekly, monthly) or custom cron expressions
- **Due Dates & Reminders**: with notification system (in-app, email, webhook)
- **Priorities**: high, medium, low with visual indicators
- **Tags/Categories**: user-defined custom tags for task organization
- **Search, Filter, Sort**: full-text search on title/description, multi-criterion filtering (status, priority, tag, due date), sorting by multiple fields

### Part B – Local Deployment with Dapr (Minikube) (MUST be implemented)
- Deploy full Todo application to Minikube
- Deploy Dapr sidecars on Minikube with **ALL building blocks**:
  - **Pub/Sub**: Kafka topics (task-events, task-updates, reminders)
  - **State Store**: PostgreSQL/Neon for storing reminder state, scheduling data
  - **Bindings**: Cron bindings for recurring task scheduling and reminder triggers
  - **Secrets**: Secrets management (environment variables, API keys)
  - **Service Invocation**: inter-service communication (e.g., backend calls reminder service)

### Part C – Cloud Deployment (Production-grade) (MUST be implemented)
- **Cloud Kubernetes**: Deploy to one of Azure AKS, Google GKE, or Oracle OKE (Oracle always-free tier recommended)
- **Dapr on Cloud**: Deploy Dapr on cloud cluster with **full building blocks** matching Part B
- **Kafka**: Either self-hosted via Strimzi operator OR managed service (Redpanda Cloud preferred, Confluent Cloud, CloudKarafka, Aiven)
- **Kafka Topics**: task-events, task-updates, reminders (with proper partitioning and retention)
- **CI/CD Pipeline**: GitHub Actions for build → test → push images → deploy via Helm
- **Monitoring & Logging**: Prometheus/Grafana/Loki or cloud-native equivalents
- **GitOps**: Infrastructure-as-Code with Git as source of truth (ArgoCD or Flux preferred)

## Quality & Style Guidelines

### General (Phases 1-3)
All code must be clean, readable, and well-commented. Use English docstrings & comments. Follow PEP 8 (backend) and prettier defaults (frontend). Prefer async/await over blocking calls. Use type hints everywhere possible. Write self-documenting code (good names > comments). Avoid magic strings/numbers — use constants or enums when appropriate. Ensure all database operations are async. This ensures maintainable, professional-quality code.

### Phase 4 Deployment-Specific
- **Multi-stage Dockerfiles** → minimal, optimized images
- **Non-root users** in containers (security)
- **No secrets in images or Git** (use .env files & Kubernetes Secrets)
- **Helm chart parameterized** (values.yaml for all deployment variables)
- **Include liveness/readiness probes** (pod health checks)
- **Health checks & startup probes** (graceful initialization)
- **Use Minikube addons**: ingress, metrics-server (for observability)
- **Document all commands & troubleshooting** (in deployment.md & README)

## Required Environment Variables (Phase 5)

**Development** (stored in `.env`, never committed to Git):
- `DATABASE_URL=postgresql://[user]:[password]@[host]/[dbname]?sslmode=require`
- `BETTER_AUTH_SECRET=[your-jwt-secret]`
- `COHERE_API_KEY=[your-cohere-api-key]`
- `OPENAI_API_KEY=[your-openai-api-key]`
- `NEXT_PUBLIC_OPENAI_DOMAIN_KEY=[chatkit-domain-key]`
- `KAFKA_BOOTSTRAP_SERVERS=localhost:9092` (or managed Kafka endpoint)

**Production** (managed via external-secrets operator or cloud KMS):
- All above variables injected via Kubernetes Secrets at runtime
- Never hardcoded in images or deployment manifests
- Rotated regularly via secret manager
- Audited for compliance (no logs contain secret values)

All secrets **MUST** be secured; no exceptions. `.env` file **MUST** be in `.gitignore`.
