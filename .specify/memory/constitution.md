# Todo Phase 3 Constitution: AI Todo Chatbot (Full Integration)

## Core Principles

### Specification-Driven Development (NON-NEGOTIABLE)
All implementation must be derived from approved Markdown specs located in `/specs/`. No agent may write code without an approved relevant spec. This ensures traceability and quality control throughout the development process.

### Strict Agent Boundaries
Agents have strict boundaries: Spec Writer → only creates/refines specs (never code); Architecture Planner → only creates planning documents; Database Engineer → only writes SQLModel models in `/backend`; Backend Engineer → only writes FastAPI code in `/backend`; Frontend Engineer → only writes Next.js code in `/frontend`; ChatKit Frontend Agent → only configures ChatKit and chat UI; MCP Engineer → only implements MCP server and tools; AI Agent Engineer → only implements OpenAI Agents SDK runner and prompt logic; Integration Tester → only runs/tests after others report completion. This ensures focused responsibility and reduces cross-contamination.

### Multi-User Security Enforcement
Every task and conversation belongs to exactly one user (enforced via `user_id`). No endpoint or UI may show tasks from other users. All API endpoints that read/write tasks or conversations **must** verify JWT and match `user_id`. This ensures data isolation between users.

### Spec Approval Requirement
Every coding agent (Database, Backend, Frontend, MCP, AI Agent) **must** ask: "Are the relevant specs (e.g. API + Database / UI + Chat / MCP + Agent) approved?" before generating any code. This ensures all implementations are properly specified first.

### No Manual Coding Outside Claude Code
All code must be generated by Claude Code based on specs. Manual edits are only allowed to fix formatting or very minor typos — never logic. This maintains consistency and traceability of all changes.

## Technology & Stack Decisions

### Monorepo Structure
The project follows this structure: `frontend/` (Next.js 16+ App Router, TypeScript, Tailwind, ChatKit), `backend/` (FastAPI + SQLModel + Alembic + OpenAI Agents SDK), `specs/` (features/api/database/ui/mcp/agent/chat), `skills/` (reusable code snippets), `subagents/`, `tests/`, `migrations/`, `docker-compose.yml`, `.env.example`, and `constitution.md`. This ensures organized separation of concerns.

### Frontend Stack
Frontend uses Next.js 16+ (App Router), TypeScript (strict), Tailwind CSS (utility classes only), Better Auth (with JWT plugin enabled), OpenAI ChatKit (conversational UI), Server Components by default, Client Components only when necessary, and a centralized API client (`lib/api.ts`) with automatic JWT header attachment. Environment: `NEXT_PUBLIC_OPENAI_DOMAIN_KEY` (domain allowlist). This provides a modern, secure frontend with conversational UI.

### Backend Stack
Backend uses FastAPI (async), SQLModel (ORM + Pydantic models), Neon PostgreSQL (serverless), JWT verification using `BETTER_AUTH_SECRET`, Alembic for migrations, OpenAI Agents SDK (agent + runner + tool calling), Cohere API (primary LLM for chat completions), dependency injection for current user (`Depends(get_current_user)`), and async SQLAlchemy sessions. This ensures a robust and scalable backend with AI capabilities.

### AI / Chatbot Stack
LLM: Cohere (primary) + OpenAI Agents SDK (tool orchestration). MCP: Official MCP SDK (5 tools: add_task, list_tasks, complete_task, delete_task, update_task). Chat endpoint: POST `/api/{user_id}/chat` (stateless). Conversation state: stored in Neon DB (Conversation + Message models). This enables stateless conversational AI with persistent state.

### Authentication & Security
Better Auth handles signup/signin/session on frontend, backend verifies JWT on protected endpoints, JWT payload contains `sub` = user_id (integer), token validation failure → 401 Unauthorized, wrong user_id in path → 403 Forbidden. All protected API endpoints must validate JWT and match user_id. This enforces secure authentication and authorization.

### Database Design
Database tables include `users`, `tasks`, `conversations`, and `messages`, with `tasks.user_id` and `conversations.user_id` as foreign keys to `users.id`. All task and conversation queries **must** filter by authenticated `user_id`. This ensures user data isolation at the database level.

### Error Handling
Return correct HTTP status codes: 400 – validation error, 401 – missing/invalid token, 403 – authenticated but not authorized (wrong user), 404 – resource not found, 500 – unexpected server error (minimal info to client). For chat endpoints, return friendly error messages in the response. This provides consistent error responses.

## Phase 3 Chatbot Requirements (must be satisfied)

- Natural language interface for all 5 core Todo features
- Stateless server (conversation state in DB)
- AI uses MCP tools via OpenAI Agents SDK
- Primary LLM = Cohere (via Cohere API key)
- Fallback / tool orchestration via OpenAI Agents SDK
- Confirmations & graceful error handling in every response
- ChatKit UI (frontend) → calls /api/{user_id}/chat
- Full multi-user isolation
- Resumable conversations (after page refresh / server restart)

## Quality & Style Guidelines

All code must be clean, readable, and well-commented. Use English docstrings & comments. Follow PEP 8 (backend) and prettier defaults (frontend). Prefer async/await over blocking calls. Use type hints everywhere possible. Write self-documenting code (good names > comments). Avoid magic strings/numbers — use constants or enums when appropriate. Ensure all database operations are async. This ensures maintainable, professional-quality code.

## Workflow Rules

1. Spec Writer creates/refines spec → gets approval
2. Architecture Planner updates architecture.md if needed
3. Database Engineer implements models/migrations (if schema changed)
4. MCP Engineer implements MCP server and tools
5. AI Agent Engineer implements agent & runner logic
6. Backend Engineer implements chat endpoint & integration
7. Frontend/ChatKit Engineer implements ChatKit UI & integration
8. Integration Tester runs full flow verification
9. Fix bugs → update spec first → re-implement

This sequential workflow ensures proper coordination between team members and prevents conflicts.

## Governance

Specifications are the single source of truth. No manual coding outside of Claude Code. Agents have strict boundaries. Always ask for spec approval. Multi-user & Security is non-negotiable. MCP tools must be stateless. Conversation state must be persisted in database. This constitution is binding for all agents during Phase 3. Any proposed deviation must be explicitly discussed and approved. All implementations must comply with these governance rules.
