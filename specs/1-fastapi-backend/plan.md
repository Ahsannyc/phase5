# Backend Technical Plan: FastAPI + SQLModel + Neon PostgreSQL

## 1. Technical Context

### Feature Overview
- **Feature**: Backend API for multi-user Todo web application
- **Requirements**: Secure, scalable backend using FastAPI, SQLModel, and Neon PostgreSQL with JWT authentication and proper user isolation
- **Primary Goal**: Create a RESTful API that integrates seamlessly with the AI-themed frontend

### Implementation Approach
- **Framework**: FastAPI (async routes)
- **ORM**: SQLModel (combines SQLAlchemy + Pydantic)
- **Database**: Neon Serverless PostgreSQL
- **Authentication**: JWT verification using PyJWT + BETTER_AUTH_SECRET
- **Dependency Injection**: FastAPI Depends() for current_user & DB session
- **Migration tool**: Alembic
- **Environment**: python-dotenv + pydantic-settings

### Known Constraints
- Must integrate with existing AI-themed frontend
- Need to share BETTER_AUTH_SECRET with frontend
- User isolation required (tasks filtered by authenticated user_id)
- All operations must be async
- CORS must allow frontend origin (http://localhost:3000)

## Phase 0: Research & Unknown Resolution

### Research Summary

#### Decision: Async Architecture
- **Rationale**: Using FastAPI with async routes and SQLModel with async SQLAlchemy provides optimal performance for a multi-user application. The async architecture handles concurrent user requests efficiently.
- **Alternatives considered**: Synchronous architecture vs async
- **Choice justification**: The async approach aligns with Neon Serverless PostgreSQL's strengths and provides better scalability for a multi-user application.

#### Decision: JWT Implementation
- **Rationale**: Using PyJWT with BETTER_AUTH_SECRET provides seamless integration with the frontend Better Auth system while maintaining security.
- **Alternatives considered**: OAuth2 vs JWT vs Sessions
- **Choice justification**: JWT approach allows stateless authentication that matches frontend expectations and enables user isolation without storing session data.

#### Decision: Migration Strategy
- **Rationale**: Alembic provides robust migration capabilities for managing database schema changes.
- **Alternatives considered**: Manual migrations vs Alembic vs other tools
- **Choice justification**: Alembic is the standard for SQLAlchemy-based applications and integrates well with SQLModel.

#### Decision: Dependency Injection Pattern
- **Rationale**: Using FastAPI Depends() for current_user and database sessions provides clean separation of concerns and testability.
- **Alternatives considered**: Global variables vs DI vs context managers
- **Choice justification**: DI pattern is idiomatic for FastAPI and provides proper error handling and resource management.

## Phase 1: Design & Contracts

### Data Model: Backend Todo Application

#### Entities

**User Entity**
- **Fields**:
  - `id`: int (primary key, auto-increment)
  - `email`: str (unique, indexed)
  - `password_hash`: str (hashed with bcrypt or argon2)
  - `name`: str (optional)
  - `created_at`: datetime (default now)
- **Validation**:
  - `email` must be a valid email format
  - `email` must be unique
  - `password_hash` length validation
- **Relationships**:
  - One user to many tasks (foreign key: tasks.user_id)

**Task Entity**
- **Fields**:
  - `id`: int (primary key, auto-increment)
  - `user_id`: int (foreign key to users.id, indexed)
  - `title`: str (required)
  - `description`: str (optional)
  - `completed`: bool (default False)
  - `created_at`: datetime (default now)
  - `updated_at`: datetime (default now, updates on modification)
- **Validation**:
  - `title` must not be empty
  - `user_id` must reference a valid user
- **State Transitions**:
  - `pending` → `completed` when task is marked complete
  - `completed` → `pending` when task is marked incomplete

### API Contracts

#### Authentication Endpoints
```
POST /api/auth/signup
- Request: { email: string, password: string, name?: string }
- Response: 201 { user: { id: int, email: string }, token: string }

POST /api/auth/signin
- Request: { email: string, password: string }
- Response: 200 { user: { id: int, email: string }, token: string }
```

#### Task Management Endpoints
```
GET /api/tasks
- Headers: Authorization: Bearer {token}
- Response: 200 [Task...]

POST /api/tasks
- Headers: Authorization: Bearer {token}
- Request: { title: string, description?: string }
- Response: 201 Task

GET /api/tasks/{id}
- Headers: Authorization: Bearer {token}
- Response: 200 Task | 403 Not authorized | 404 Not found

PUT /api/tasks/{id}
- Headers: Authorization: Bearer {token}
- Request: { title?: string, description?: string }
- Response: 200 Task | 403 Not authorized | 404 Not found

DELETE /api/tasks/{id}
- Headers: Authorization: Bearer {token}
- Response: 204 No Content | 403 Not authorized | 404 Not found

PATCH /api/tasks/{id}/complete
- Headers: Authorization: Bearer {token}
- Request: { completed: boolean }
- Response: 200 Task | 403 Not authorized | 404 Not found
```

### Quickstart Guide

#### Initial Setup
1. Navigate to the backend directory: `cd backend`
2. Install dependencies: `pip install -r requirements.txt`
3. Set up environment variables in `.env` file:
   ```
   DATABASE_URL=postgresql://...
   BETTER_AUTH_SECRET=...
   BETTER_AUTH_URL=http://localhost:3000
   ```
4. Run migrations: `alembic upgrade head`
5. Start the server: `uvicorn app.main:app --reload`

#### Running the Application
1. Ensure Neon PostgreSQL database is accessible
2. From the backend directory, run: `uvicorn app.main:app --reload`
3. The API will be available at `http://localhost:8000`

#### Key Development Commands
- `uvicorn app.main:app --reload` - Start development server
- `alembic revision --autogenerate -m "description"` - Create migration
- `alembic upgrade head` - Apply migrations
- `pytest` - Run tests
- `black .` - Format code
